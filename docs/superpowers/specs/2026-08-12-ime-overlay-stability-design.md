# NextSay 输入法事件下的悬浮面板稳定性设计

## 问题

在 QQ 或微信中打开 NextSay 白色候选面板后，点击“补充要求”并修改已有文字，搜狗输入法提交文字时可能触发窗口切换。当前服务会重新判断前台应用，导致面板从可见窗口中消失。NextSay 进程、无障碍服务和绿色浮球并未崩溃。

## 目标

- 面板打开期间可以自由输入和修改补充要求。
- 输入法弹出、输入、删除、切换中英文和收起时，面板保持可见。
- 用户真正从微信切到 QQ、从 QQ 切到微信或离开受支持应用时，旧面板仍应关闭，避免把旧上下文用于新会话。
- 不改变“只写入输入框、绝不自动发送”的安全边界。

## 方案

新增一个独立的前台事件判定策略：

1. 识别当前系统输入法包名。
2. 当事件来源是当前输入法，且 NextSay 面板已打开时，不更新活动聊天应用，也不关闭当前面板。
3. 当事件来源是微信或 QQ 的真实应用窗口时，继续使用现有前台解析逻辑；如果来源应用与面板上下文不同，关闭旧面板。
4. 当用户离开所有受支持聊天应用时，继续移除面板和浮球。

策略做成不依赖 Android UI 的纯 Kotlin 单元，服务只负责提供事件来源、当前输入法包、面板是否打开和解析后的前台包。

## 错误处理

- 无法取得默认输入法包名时，不把任意第三方包当作输入法；沿用现有前台判断。
- 输入法事件期间若当前面板本身不存在，不拦截正常的应用切换判断。
- 面板输入不会写入聊天历史，也不会进入日志；只有用户点击“生成回复”时才作为 instruction 发送给本地后端。

## 测试

自动化单元测试：

- 面板打开时忽略当前输入法事件。
- 面板关闭时不忽略输入法事件。
- 不忽略伪装成输入法的其他包。
- 微信与 QQ 之间真实切换仍关闭旧面板。
- 离开受支持应用仍关闭面板和浮球。

真机回归矩阵：

- QQ、微信分别测试空输入、已有文字追加、删除、连续修改。
- 搜狗中文、搜狗英文切换。
- 键盘展开、收起、再次展开。
- 面板打开时从微信切 QQ、从 QQ 切微信。
- 修改要求后重新生成三条候选，并验证候选只写入聊天输入框、不发送。

## 完成标准

上述单元测试、Android lint、APK 构建全部通过；荣耀 X40 真机上修改补充要求时面板不再消失，且跨应用切换安全策略仍有效。
