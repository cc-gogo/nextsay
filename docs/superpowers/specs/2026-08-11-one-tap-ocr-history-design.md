# NextSay 一键 OCR 与会话历史设计

日期：2026-08-11
状态：待用户书面确认

## 背景

真机验证表明，QQ 能通过无障碍节点读取可见聊天正文；当前微信 8.0.76 在荣耀 RMO-AN00（Android 13）上只向无障碍服务和 `uiautomator` 暴露一个空根节点，无法继续通过节点解析获取聊天内容。

本阶段不接入通知监听，不读取微信或 QQ 私有数据库，不要求 Root。采用“QQ 无障碍优先、微信本地 OCR”的混合路线。

## 目标

- 用户点击一次 NextSay 浮球后，自动完成获取当前上下文、合并本地历史、调用回复 API 和展示候选。
- 微信截图与 OCR 全程在手机本地完成；原始截图不落盘、不上传。
- 为不同单聊保存相互隔离的本地文字历史，下次打开同一单聊时继续追加。
- 热启动时，本地截图、OCR 和历史合并争取在 1 秒内完成。
- 保持现有安全边界：候选只写入输入框，绝不自动点击发送。

## 非目标

- 第一版不支持微信群聊的长期成员级历史。
- 不识别图片、表情、文件、引用卡片或语音的具体内容，只允许保存类型占位符。
- 不从通知、备份、Root、Hook 或微信私有数据库补全屏幕外历史。
- 不承诺区分显示昵称完全相同的两个微信联系人。
- 不持续录屏，不在后台定时截图；只有用户点击浮球才执行一次。

## 方案选择

### 方案 A：截图上传视觉模型

实现最直接，也可能获得更强的界面理解能力，但原始聊天截图会离开设备，延迟、费用和隐私风险最高。本阶段不采用。

### 方案 B：所有应用统一 OCR

代码路径统一，但会放弃 QQ 已有的结构化节点、降低准确率并增加耗时。本阶段不采用。

### 方案 C：无障碍优先，OCR 回退

QQ/TIM 优先使用无障碍节点；微信或无障碍上下文为空时使用本地 OCR。该方案兼顾准确率、速度和隐私，为本阶段采用方案。

## 一键交互

1. 用户点击浮球，浮球立即显示按压波纹并触发清晰的确认触感。
2. NextSay 冻结重复点击并显示“正在识别当前对话”。
3. QQ/TIM 读取无障碍节点；微信隐藏浮球一个渲染帧后调用无障碍截图，再恢复浮球。
4. 微信在本地识别标题和可见聊天气泡，原始位图随后立即释放。
5. 识别结果与该会话的本地历史合并并保存。
6. NextSay 自动选择最近的有效上下文并调用现有回复 API，不再要求第二次确认上传。
7. 面板显示本次识别到的具体消息和“正在生成”；API 返回后展示候选。
8. 用户点击候选后，NextSay 只将文字写入输入框，仍由用户检查并手动发送。

点击浮球是本次截图、文字上传和生成回复的明确授权。设置页和首次使用说明必须明确告知这一行为。

## 组件边界

### `ContextCaptureCoordinator`

接收当前前台包名并选择上下文来源。QQ/TIM 调用现有节点捕获器；微信调用截图 OCR。它只负责调度，不解析布局或访问数据库。

### `LocalScreenshotSource`

使用 Android 11 以上的 `AccessibilityService.takeScreenshot()` 获取单帧位图。服务配置声明截图能力。截图前临时隐藏 NextSay 浮层，避免按钮和面板进入 OCR；截图完成、失败或超时后都必须恢复浮球。

### `WechatOcrParser`

使用随 APK 打包的离线中文文字识别模型，避免依赖 Google Play 服务和首次联网下载。解析器接收 OCR 文字块及其边界框，输出：

- 顶部标题候选；
- 按纵向顺序排列的消息；
- 根据气泡文字块横向中心判断的 `ME`、`OTHER` 或 `UNKNOWN`；
- 图片、语音等可以可靠判断时的类型占位符。

解析器排除状态栏、标题栏控件、输入区、键盘和 NextSay 浮层区域。低置信度文字不进入长期历史。

### `ConversationIdentityResolver`

第一版微信会话键为 `com.tencent.mm + 规范化后的顶部显示标题`。规范化只处理首尾空白和稳定的界面后缀，不进行模糊昵称合并。

微信不向 NextSay 提供内部联系人 ID，因此该键不是全局唯一标识。第一版以“单聊显示标题在用户联系人中唯一”为长期保存前提。两个联系人显示昵称完全相同时会得到相同键，系统无法自动判断；用户必须能够将某个标题标记为“不保存长期历史”，此后该标题只使用当前屏幕生成。系统不得通过头像猜测后静默拆分。群聊只生成当前屏幕回复，不写入长期会话历史。

QQ/TIM 在能取得稳定会话标题时采用同样的应用包名加标题键；取得不到标题时沿用当前仅使用可见上下文的行为。

### `ConversationHistoryStore`

使用本地 Room 数据库存储会话和消息。建议数据结构：

- `ConversationRecord`：本地 ID、来源包名、规范化标题、显示标题、类型、创建和更新时间；
- `MessageRecord`：会话 ID、角色、规范化正文、显示正文、首次发现时间、来源和置信度；
- `CaptureRecord`：会话 ID、捕获时间、合并结果和失败类型，不保存截图或正文日志。

数据库位于 NextSay 应用沙箱。消息正文使用 Android Keystore 管理的密钥进行本地加密；日志不得包含聊天正文、标题或 API 请求体。

### `HistoryMerger`

合并时比较“角色 + 规范化正文”的消息序列，寻找本地历史后缀与当前屏幕前缀之间的最长连续重叠，仅追加重叠后的消息。

该算法不会仅凭单条文本哈希去重，因此连续出现两个“好的”仍可保留。没有可靠重叠时，当前屏幕只用于本次生成，不直接整段追加到长期历史，避免滚动位置变化导致重复污染。

### `GenerationContextBuilder`

从长期历史与本次可见上下文中选择最近消息，按现有 `ChatContext` 格式交给后端。默认上限由消息条数和总字符数共同控制，初始建议为最近 20 条且不超过 3000 个中文字符。文本脱敏继续在上传前执行。

## 状态流

主流程状态为：

`Idle -> Capturing -> Recognizing -> Merging -> Generating -> Results`

任一阶段失败进入 `Error`。新点击在非 `Idle`、`Results`、`Error` 状态下被忽略。前台应用变化时取消尚未发出的请求；API 已发出但会话发生变化时，其结果不得写入当前输入框。

## 错误处理

- 截图能力不可用：显示“无法截取当前微信页面”，不调用 API。
- OCR 未找到标题：显示识别到的消息用于调试，但不保存、不上传，避免串会话。
- OCR 找到标题但没有消息：不调用 API，提示调整到聊天正文后重试。
- 角色判断不确定：消息可用于本次预览，但不写入长期历史。
- 历史无法可靠重叠：保留旧历史，本次仅使用当前屏幕生成。
- 本地数据库失败：允许只用当前屏幕生成，但明确提示本次未保存历史。
- API 超时或失败：保留已经合并的本地历史，提供重试；重试不重复截图和写入。
- 截图或 OCR 抛出异常：释放位图、恢复浮球并解除点击锁。

## 性能设计

- 无障碍服务连接后异步预热 OCR 引擎，不读取屏幕。
- 截图后只保留聊天内容区域，尽早裁剪和释放全屏位图。
- 同一时刻只允许一次 OCR 和一次生成请求。
- 本地热路径目标：截图 50-150ms，OCR 200-600ms，合并低于 100ms。
- 冷启动允许 1-2 秒；点击到首个候选的整体目标为 2-5 秒，主要变量是模型 API。
- 后端支持流式返回时再增加流式候选；不作为第一版 OCR 的阻塞条件。

## 隐私与产品约束

- 一键运行会自动上传识别后的文字，首次启用时必须提供单独、明确的用途披露和用户同意。
- 原始截图不得写入文件、相册、缓存、日志或网络请求。
- 用户可以清空全部历史或删除单个会话。
- 用户可以将特定显示标题排除在长期历史之外，以规避同名联系人混合。
- 本地历史默认设置容量上限；达到上限时按最旧消息淘汰。
- 后端只接收生成所需的最近上下文，不接收完整本地数据库。
- 绝不自动发送消息，绝不在未点击浮球时截图或上传。

## 测试与验收

### JVM 测试

- 捕获协调器对 QQ 选择无障碍、对微信选择 OCR、空节点时回退 OCR。
- OCR 布局解析覆盖左右角色、纵向排序、区域过滤和低置信度文本。
- 会话标识规范化覆盖空标题、稳定标题和被排除标题。
- 历史合并覆盖完整重叠、部分重叠、重复短句、无重叠和角色变化。
- 状态机覆盖重复点击、应用切换、截图失败、OCR 失败、API 重试和旧结果失效。
- 上传上下文覆盖最近 20 条、字符上限和上传前脱敏。

### 仪器化测试

- 使用不含真实聊天内容的固定测试位图验证离线中文 OCR 能运行。
- 验证截图完成和异常时位图释放、浮球恢复。
- 验证 Room 会话隔离、加密字段往返和历史清理。

### 真机验收

- 微信单聊：点击一次后自动显示识别正文并生成候选，原始截图不落盘。
- 同一联系人：滚动或收到新消息后再次运行，只追加新内容。
- 不同联系人：历史互不混合；返回旧联系人时能继续使用其历史。
- QQ 单聊：继续使用无障碍正文，不引入 OCR 性能回退。
- 触摸反馈：浮球和候选都有清晰波纹与触感，快速连点只触发一次。
- 写入候选：文字进入当前输入框但不自动发送。
- 性能：热启动 OCR 小于 1 秒，整体等待时间主要由 API 决定。
